# 持续 CPU Profiling 监控与诊断思路

## 背景问题

凌晨 3 点 CPU 飙升这类故障的核心难点不是“不会分析 CPU”，而是“故障现场消失得太快”。值班同学赶到时，`perf top` 只能看到当前时刻的调用栈，无法回答事故发生时谁在消耗 CPU。

因此工具目标不是替代 Prometheus、日志或 APM，而是补上 CPU 调用栈这一类关键现场证据。

## 可能原因清单

### 应用层代码路径异常

- 定时任务在凌晨集中执行，例如清理历史数据、重建索引、批量同步、报表生成。
- 热 key、热点用户或异常请求触发复杂计算路径。
- 重试风暴、消息重复消费、限流失效导致请求量瞬时放大。
- 代码进入意外循环、递归、退化算法，例如 O(n) 变 O(n²)。
- 正则表达式灾难性回溯、JSON/压缩/加解密等 CPU 密集逻辑被异常放大。

### 运行时与语言层问题

- JVM GC、JIT 编译、Safepoint、偏向锁撤销、类加载或反射热点。
- Go GC、调度器抢占、goroutine 泄漏、map/hash 热点。
- Python/Ruby/Node.js 单线程事件循环被 CPU 密集任务阻塞。
- native 扩展或 C/C++ 依赖库消耗 CPU，但业务日志不可见。

### 并发与锁竞争

- 自旋锁、CAS 失败重试、用户态锁竞争导致 CPU 空转。
- 线程池被打满后出现忙等、轮询、重复抢锁。
- 队列空转拉取、消费者无退避。
- 内核态 futex、调度开销异常。

### 系统与内核层问题

- 内核网络协议栈、软中断、iptables/eBPF、conntrack 等消耗 CPU。
- page fault、内存回收、NUMA 迁移、透明大页整理。
- 文件系统、压缩、加密、校验等内核路径异常。
- 容器 cgroup CPU throttle、绑核策略、抢占或 noisy neighbor。

### 外部流量与依赖问题

- 上游批量调用、爬虫、攻击流量或流量回放。
- 下游超时导致同步调用堆积和重试。
- MQ 积压释放，消费者集中追赶。
- 配置发布、特征开关或降级策略在低峰时段触发异常路径。

## 监控组合思路

持续 CPU Profiling 只解决“当时 CPU 在跑什么”。生产定位还需要把调用栈与时间线对齐：

- 指标：CPU 使用率、load、run queue、上下文切换、软中断、GC、QPS、延迟、错误率、线程数。
- 日志：定时任务开始/结束、配置变更、批处理批次、重试与降级事件。
- 事件：发布、扩缩容、迁移、数据库维护、流量调度。
- Profile：对应时间窗口的 `perf.data`、folded stack、flamegraph。

## Profiling 采集策略

### 常驻低开销采样

推荐默认使用固定频率采样，例如 49Hz 或 99Hz。频率低于线上调试常用值，既能保留足够趋势，又能控制开销。对极高 QPS 服务可从 49Hz 起步。

### 时间切片与环形保留

以固定窗口保存 profile，例如每 60 秒一个 `perf.data`：

```text
profiles/
  2026/05/09/03/
    cpu-profiler-20260509T030000+0800.perf.data
    cpu-profiler-20260509T030100+0800.perf.data
    index.jsonl
```

查询故障时间 `03:17:42` 时，工具自动选择包含该时间点的窗口，也可以追加前后 N 分钟合并分析。

### 采集目标

- system-wide：适合先发现是应用、内核还是其他进程。
- PID：适合固定进程，缺点是进程重启后 PID 变化。
- 进程名：适合服务重启场景，需要定期解析 PID。
- cgroup/container：适合容器化部署，是生产环境推荐方式。

### 栈展开策略

- 默认使用 frame pointer，开销低、稳定，但需要应用编译保留 frame pointer。
- 可选 DWARF unwind，信息更完整但开销和 profile 体积更高。
- 对 JVM/Go/Node 等运行时，需要在 README 中明确额外符号、JIT map 或运行时参数建议。

### 查询与火焰图

查询流程：

1. 用户输入故障时间、服务标识和时间范围。
2. 工具定位相关 `perf.data` 文件。
3. 执行 `perf script` 解析采样。
4. 折叠调用栈，生成 folded stack。
5. 调用 FlameGraph 生成 SVG。
6. 输出火焰图路径和采样摘要。

### 生产防护

- 磁盘配额：超过上限后按时间删除旧数据。
- CPU 开销限制：默认低频采样，支持动态降级或暂停。
- 权限预检：检查 `perf_event_paranoid`、capability、内核符号访问。
- 健康检查：采集进程存活、最近切片时间、文件大小、错误计数。
- 自监控指标：采集延迟、丢样、磁盘占用、生成失败次数。
- 故障隔离：perf 异常退出后重启，连续失败进入退避。

## 与传统监控的关系

Prometheus 告诉我们“什么时候 CPU 高了”，日志告诉我们“业务做了什么”，持续 profiling 告诉我们“CPU 当时花在哪里”。三者结合才能把“猜测复盘”变成“证据复盘”。
